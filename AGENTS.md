AGENTS.md — инструкции для AI-агентов
1. Назначение проекта
Репозиторий содержит клиент-серверное приложение:
- Клиент: Flutter / Dart (мобильное, веб- или десктопное приложение — в зависимости от фактической конфигурации проекта).
- Сервер: Go (HTTP API, бизнес-логика, интеграции и работа с данными).
- Взаимодействие: через API, формат и правила которого определяются существующим контрактом проекта.
Цель агента — вносить небольшие, проверяемые, безопасные изменения, соблюдая существующую архитектуру. Не заменяй применяемые библиотеки, инструменты и паттерны без необходимости.
Где искать код
Сначала изучи фактическую структуру репозитория. Если проект организован как монорепозиторий, типичная структура выглядит так:
client/                   # Flutter-приложение (lib/, test/, pubspec.yaml)
server/                   # Go-сервис (go.mod, исходный код, тесты)
api/                      # Контракт API, например OpenAPI (если есть)
README.md                 # Запуск и устройство проекта
AGENTS.md                # Эти инструкции
Это пример, а не требование. Папки могут называться app/, frontend/, backend/ и иначе. Используй реально существующие пути. Вложенные файлы AGENTS.md, если они есть, уточняют правила для соответствующих каталогов.
2. Приоритеты и ограничения
1. Следуй задаче пользователя, существующему коду, README.md, конфигурации CI и применимым AGENTS.md.
2. Соблюдай обратную совместимость API и существующее поведение, если изменение не запрошено явно.
3. Изменяй только файлы, необходимые для задачи. Не делай попутный массовый рефакторинг.
4. Не добавляй зависимости, архитектурные слои или генераторы кода без обоснованной необходимости. Предпочитай используемые в проекте решения.
5. Не записывай в репозиторий пароли, токены, приватные ключи, настоящие персональные данные и содержимое .env с секретами.
6. Не изменяй вручную сгенерированные файлы (*.g.dart, *.freezed.dart, protobuf/OpenAPI-клиенты и т. п.). Меняй исходники и запускай существующую генерацию.
7. Не запускай без явного разрешения разрушительные команды: удаление данных, сброс БД, git reset --hard, принудительную очистку, публикацию или деплой.
8. Не коммить и не отправляй изменения в удалённый репозиторий без отдельного запроса.
9. Если нет доступа к необходимой зависимости, сервису или среде выполнения, явно сообщи об ограничении; не выдавай непроверенное за проверенное.
3. Рабочий процесс агента
Перед изменениями
- Прочитай релевантные README.md, AGENTS.md, pubspec.yaml, go.mod, конфигурации линтеров, CI и существующие тесты.
- Проверь git status и сохрани пользовательские несохранённые или незакоммиченные изменения.
- Найди уже реализованные аналогичные сценарии и используй их как образец.
- Для нетривиальной задачи составь краткий план: затрагиваемые части клиента, сервера, контракта и тестов.
- Уточняй требования только тогда, когда без этого невозможно безопасно выбрать поведение. В остальных случаях принимай минимальные решения, согласованные с кодовой базой, и перечисляй допущения.
Во время изменений
- Реализуй задачу по вертикали: API/хранилище → клиентский слой данных → UI, только если все эти уровни затронуты.
- Не дублируй бизнес-правила на клиенте и сервере. Сервер — источник истины для авторизации, доступа к данным и критичных бизнес-ограничений.
- Если меняется API, синхронизируй сервер, контракт, клиентские модели и тесты.
- Предпочитай маленькие функции, явные типы, понятные имена и обработку ошибок вместо скрытых побочных эффектов.
- Добавляй тесты на исправленные дефекты и значимые новые сценарии.
- Не маскируй ошибки пустыми catch, фиктивными ответами или безусловным успешным результатом.
После изменений
- Отформатируй затронутые файлы и запусти доступные релевантные проверки.
- Убедись, что тесты проверяют и успешные, и ошибочные сценарии.
- Проверь git diff: нет ли лишних файлов, секретов, изменений сгенерированных артефактов или нарушения контракта.
- В итоговом сообщении укажи: что изменено, какие проверки реально выполнены, что не удалось проверить и есть ли миграции/риски совместимости.
4. Flutter / Dart — клиент
Архитектура
- Сохраняй текущее разделение на UI, управление состоянием, бизнес-логику и доступ к данным (если оно уже есть).
- Не выполняй HTTP-запросы, SQL-запросы и сложную бизнес-логику непосредственно внутри виджетов.
- Используй существующий подход к состоянию (например, BLoC, Riverpod, Provider или иной); не добавляй параллельный механизм без причины.
- Используй null safety, строгие модели данных и предсказуемую обработку async/await.
- Для сетевых операций обрабатывай загрузку, пустой результат, ошибки, тайм-ауты и повторные попытки там, где они уместны.
- Не используй BuildContext после асинхронной операции без проверки актуальности контекста (mounted, если применимо).
- Избегай ненужных перестроений виджетов, тяжёлой работы в build() и утечек контроллеров/подписок.
API и конфигурация
- Используй существующий HTTP-клиент и централизованную конфигурацию базового URL.
- Не хардкодь адреса серверов, API-ключи и значения окружений в виджетах.
- DTO, названия JSON-полей, необязательные значения и сериализация должны соответствовать контракту сервера.
- Не храни токены доступа в открытом виде; следуй установленному в проекте механизму безопасного хранения.
- Не трактуй локальную проверку роли пользователя как замену серверной авторизации.
UI и тесты
- Соблюдай существующую дизайн-систему, маршрутизацию, локализацию и подход к адаптивности.
- Учитывай состояния загрузки/ошибки, доступность и разные размеры экранов.
- Пиши unit-тесты для логики и преобразований, widget-тесты для UI-состояний, integration-тесты для критических пользовательских сценариев (если инфраструктура есть).
- Мокай внешние сетевые зависимости в изолированных тестах.
Стандартные проверки
Выполняй из каталога Flutter-проекта:
flutter pub get              # при первом запуске или изменении зависимостей
# Для изменённых Dart-файлов: dart format <пути-к-файлам>
flutter analyze
flutter test
Если проект использует генерацию кода, запускай уже настроенную команду генерации; не предполагай, что конкретный генератор установлен.
5. Go — сервер
Архитектура и стиль
- Следуй существующей организации пакетов, роутинга, конфигурации и внедрения зависимостей.
- Разделяй HTTP-транспорт, бизнес-правила и доступ к данным настолько, насколько это принято в проекте; не добавляй пустые интерфейсы и лишние абстракции.
- Сохраняй идиоматичный Go: короткие функции, явные ошибки, errors.Is/errors.As и %w при оборачивании ошибок, где это уместно.
- Передавай context.Context через сетевые, БД- и долгие операции; соблюдай отмену и тайм-ауты.
- Не используй panic для ожидаемых ошибок запроса или бизнес-логики.
- Учитывай конкурентный доступ к разделяемому состоянию; избегай гонок и зависаний горутин.
- Пользуйся уже выбранными библиотеками HTTP, логирования и БД; не меняй стек ради локальной задачи.
HTTP API
- Валидируй входные данные и явно определяй ошибки, статусы HTTP и ответы.
- Не раскрывай клиенту стектрейсы, внутренние детали БД и чувствительные данные.
- Авторизацию и проверку прав выполняй на сервере для каждого защищённого ресурса.
- Используй ограниченные тайм-ауты, корректное завершение работы сервера и структурированные логи, если инфраструктура это поддерживает.
- Соблюдай договорённости проекта об идемпотентности, пагинации, сортировке, фильтрации и версионировании API.
Данные
- Используй параметризованные запросы или принятый в проекте ORM/query builder, а не конкатенацию пользовательского ввода в SQL.
- Для изменений схемы добавляй миграции в формате существующей системы миграций; учитывай действующие данные и совместимость при развёртывании.
- Оборачивай согласованные изменения нескольких сущностей в транзакцию, когда это нужно.
- Не применяй разрушительные миграции и не очищай реальные данные без явного разрешения.
Тесты и проверки
- Пиши табличные unit-тесты там, где это повышает ясность; HTTP-обработчики проверяй через httptest, если это соответствует стеку.
- Проверяй валидацию, статусы, доступ, ошибки зависимостей и граничные случаи.
- Используй go test -race для кода с конкурентностью, если текущая платформа и инструментальная цепочка это поддерживают.
Выполняй из каталога Go-модуля:
# Для изменённых Go-файлов: gofmt -w <пути-к-файлам>
go test ./...
go vet ./...
# При необходимости: go test -race ./...
Запускай go mod tidy только при осознанном изменении зависимостей; проверяй соответствующий diff.
6. Контракт клиент ↔ сервер
- При наличии OpenAPI, protobuf или другой схемы считай её договорённым источником контракта. Если контракт пока описан только кодом, ориентируйся на фактические маршруты, модели и тесты.
- Для изменений API согласуй: URL и методы, авторизацию, заголовки, JSON-поля и типы, nullable/optional-поля, формат ошибок и HTTP-статусы.
- Сохраняй существующий стиль именования JSON (snake_case или camelCase); не переключай его самостоятельно.
- Для времени используй явно определённые контрактом формат и часовой пояс (предпочтительно RFC 3339 / UTC для новых полей, если существующие правила не противоречат).
- Не предполагай, что null, отсутствие поля, [] и {} взаимозаменяемы.
- Если изменение несовместимо с текущими клиентами, сначала предложи совместимый путь миграции или версионирование.
- Для новой функциональности добавляй хотя бы один тест контракта/обработчика на Go и тест разбора ответа либо клиентского сценария на Flutter.
7. Безопасность и конфигурация
- Конфигурация окружения должна передаваться через предусмотренный проектом механизм. В документации допустимы только фиктивные примеры значений.
- Не логируй пароли, токены, заголовки авторизации, платёжные данные и полные персональные данные.
- Проверяй ввод на границе системы; ограничивай размеры тел запросов и файлов, если применимо.
- Не отключай TLS-проверку, авторизацию, защиту от CSRF (когда она нужна), ограничения CORS или проверку сертификатов ради упрощения разработки.
- Новые внешние зависимости и доступы должны быть минимальными и обоснованными.
- Не отправляй содержимое репозитория и пользовательские данные в сторонние сервисы без необходимости и разрешения.
8. Definition of Done
Задача считается завершённой, когда:
- [ ] Реализовано именно запрошенное поведение, без несвязанных изменений.
- [ ] При изменении API согласованы клиент, сервер и контракт/документация.
- [ ] Обработаны ошибки, граничные случаи и требования безопасности.
- [ ] Добавлены или обновлены релевантные тесты.
- [ ] Затронутые Dart/Go-файлы отформатированы.
- [ ] Выполнены доступные flutter analyze, flutter test, go test ./..., go vet ./... для соответствующих частей проекта; невыполненные проверки явно перечислены.
- [ ] Изменения схемы БД, настроек запуска и переменных окружения документированы, если они есть.
- [ ] Финальный ответ кратко описывает изменения, результаты проверок и оставшиеся ограничения.
Главное правило: сначала разберись в существующем проекте, затем внеси минимальное согласованное изменение и подтверди его проверками. Не подменяй реальные факты предположениями.
